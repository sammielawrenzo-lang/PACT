# Pact deadline refunds on Vercel

The `/api/deadlines` route processes up to 20 expired pacts per call. Browser POST requests require the authenticated workspace owner and the same origin. Background requests require an exact `Authorization: Bearer <CRON_SECRET>` credential; the obsolete Sites header is never sufficient on Vercel. Choose a cryptographically random secret with at least 32 characters and keep it in Vercel runtime settings.

Supabase Cron job `pact-deadline-refunds` runs every minute (`* * * * *`) in project `vcmvpqtkeybkzvpzepjy`. It calls `https://pact-theta-one.vercel.app/api/deadlines` through `pg_net`, reading the bearer credential from Vault secret `pact_deadline_cron_secret`. `database/deadline-scheduler.sql` records the configuration without containing credentials. The job is active. A live authenticated invocation returned HTTP 200 and processed an expired simulated contribution into the refunded state. Provider-confirmed sandbox refunds still need an end-to-end payment test.

`vercel.json` also defines a deployed daily safety sweep compatible with the current Hobby plan. The browser requests a check every 30 seconds while open. The deadline makes funds due for refund; checks, retries, provider processing, and infrastructure availability can delay completion. A paused Supabase project cannot run its scheduler.

Inspect `cron.job_run_details` for scheduler executions and `net._http_response` for HTTP results. A successful SQL job means the HTTP request was queued; confirm its HTTP status and response too. Never log the request headers or decrypted Vault values. The expected success body contains `checked`, `completed`, and `pending`. A nonzero `pending` requires reconciliation rather than assuming money was returned. To pause only this job, use `cron.alter_job(jobid, active := false)` with the ID selected by job name. Keep Vercel `CRON_SECRET` and the Vault value synchronized; redeploy Vercel after changing the environment value.

The database stores provider operation IDs, versions, and leases. Only the server can update financial state. Clients have an owner-only read policy and no write grants. Updates compare the stored version atomically, so stale requests cannot overwrite newer payment state. Pending refunds remain eligible for retries. Payouts already reserved before expiry stay on their existing reconciliation path.

All provider requests use the PayPal sandbox API. Captures go into the configured sandbox business account; refunds go to the original captures. No live-money or escrow claim is made. Never share Supabase secret keys, PayPal secrets, cron credentials, or OpenAI keys in source, browser bundles, screenshots, or logs.

Supabase security review found no missing RLS or exposed-extension issue after moving the new `pg_net` installation to `extensions`. The remaining Auth advisory is disabled leaked-password protection; Pact currently uses email links rather than passwords. Review https://supabase.com/docs/guides/auth/password-security#password-strength-and-leaked-password-protection before introducing password sign-in.
